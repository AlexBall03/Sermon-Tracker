# Handoff: PS-A4.2B, Personal Appearance Preset Infrastructure

4 November 2026. Branch `dev`, from `0c27feb` ("Phase A4.2A is done"). Not committed: every change is unstaged for the owner's review. No migration was applied to any shared database.

A4.2B is the storage and server side of personal appearance presets: an account's own saved appearances, an account default, and everything that keeps them correct under retries, concurrency, and account deletion. It has no screens. A4.2C (My Presets, Save as Preset, applying a preset, new outlines from the default) is approved and not built.

## Owner decisions applied

1. **Contents.** A preset is an A4.2A `AppearanceSnapshot`: the built-in preset and its revision, the outline-wide defaults, named styles, component-type styles, levels 1 to 32, number presentation, and numbering. It never holds sermon content, passages, document, outline, or component IDs, a node's own appearance, structure, or view state.
2. **Independent snapshots.** A preset is a source that is copied when applied. Nothing in a document names one, and renaming, changing, or deleting one changes no outline.
3. **Account default.** Minimal, Balanced, Expressive, or one of the account's own presets. Balanced for new and existing accounts until chosen otherwise. Existing documents are never restyled.
4. **Deleting the default** sets the account back to built-in Balanced and deletes the preset in one transaction, or does neither.
5. **Online only.** No offline queue, IndexedDB, background sync, or automatic retry for presets.
6. **Application** (A4.2C) goes through `snapshotDraft`, the existing preview, validation, conflict checks, `applyAppearanceDraft`, and Undo; single components are kept.
7. **Idempotency** (decided during planning): a dedicated ledger, `appearance_preset_operations`, with at least 30 days' retention and opportunistic pruning.
8. **Race testing** (decided during planning): on a disposable local PostgreSQL, with no change to the project's dependencies and nothing left running.
9. **Refinements to the approved plan:**
   - schema-valid and storable snapshots are distinguished, and the largest valid one is measured, not assumed to fit;
   - retention is documented as "at least", and a reused operation ID never alters an existing preset;
   - constraint failures are mapped only after their transaction ended;
   - the rollback limitation and its recovery are documented;
   - race tests assert the committed state (95 + 20 creates: exactly 5 succeed, 100 at the end).

## Schema (migration `0021_appearance_presets`)

Generated by `npm run db:generate -- --name=appearance_presets`; not edited. Full description in `docs/DATABASE.md` ("Personal appearance presets" and "A4.2B migration").

- **`appearance_presets`**:
  - columns: `id` (server-made UUID), `owner_id → users.id RESTRICT`, `name`, `appearance jsonb`, `revision` (1, CHECK ≥ 1), and `created_at`/`updated_at`;
  - `name`: CHECK 1–80 characters after trimming, and stored trimmed;
  - `appearance`: CHECK that it is an object and that `octet_length(appearance::text) <= 65536`;
  - keys and indexes: unique index `(owner_id, lower(name))`, which also serves the list order and the owner key; `UNIQUE (id, owner_id)`. No other index.
- **`appearance_preset_operations`** (the ledger):
  - PK `(owner_id, operation_id)`;
  - `kind` (`create` or `duplicate`);
  - `preset_id` (no key; it outlives the preset);
  - `fingerprint` (64 hex characters);
  - `created_at`;
  - `owner_id → users.id RESTRICT`. No content.
- **`users`**:
  - `default_builtin_appearance_preset` (`balanced` default, CHECK on the three ids);
  - `default_personal_appearance_preset_id`;
  - `appearance_default_revision` (1, CHECK ≥ 1);
  - CHECK exactly one of the two defaults;
  - **`users_default_appearance_preset_fk (default_personal_appearance_preset_id, id) → appearance_presets (id, owner_id) RESTRICT`**: a default can only be the account's own preset, whatever writes the row.
- **Circular keys.** Drizzle declares the composite key in `users`' extra-config callback, which is evaluated lazily, and the presets' owner reference is typed `(): AnyPgColumn => users.id`. The generated SQL creates both tables, then the columns, then every key, then the index and CHECKs. That order was reviewed and is asserted by the migration test.
- **Additive and backward compatible:**
  - constant defaults, so no row is rewritten;
  - every existing account reads Balanced, null, 1;
  - the live code's inserts and deletes of accounts still work (tested);
  - no `UPDATE`, `DROP`, rename, or column change.
- **`AppUser`** gains the three columns. The administrator's directory leaves them out (`DirectoryEntry`, `admin/clerk.ts`), as it does other per-account preferences.

## Snapshot format, validation, and materialization (`model.ts`)

`prepareAppearance(input)` is the only way an appearance becomes storable:

1. `toPlainJson` (A2.3A.1): refuses `undefined`, `NaN`, a `Date`, a U+0000, and anything else JSON or `jsonb` would change.
2. `appearanceSnapshotSchema` (A4.2A, unchanged): version 1 only, built-in revision 1 or 2 only, every value in bounds, levels "1"–"32".
3. `hasUnknownKeys`: any key in the input that the parsed result lacks is refused. The snapshot schema is strict, but the numbering schema it includes would silently drop unknown keys. Defaults the numbering schema fills in are not a difference.
4. `materialize`: the built-in revision's code values are written in under the person's own, so the preset keeps its look whatever later built-in revisions do.
5. Parsed again, then measured.

On every read, `readStoredAppearance` validates the stored snapshot again. One that does not parse is `unreadable`, and is never repaired or replaced.

Revisions 1 and 2 are untouched. A preset materialized at revision 1 keeps revision 1's values (tested with Minimal's script, which differs in revision 2). Nothing re-resolves a stored snapshot against newer built-ins.

As A4.2A says, theme colors still follow the theme and CSS-only treatments (a note's per-kind shapes) still follow the CSS; nothing here serializes CSS.

**Size.** The limit is on what PostgreSQL stores: jsonb's own text, which is never shorter than compact JSON (it adds `": "` and `", "`). The application refuses early what is over as compact JSON, and the CHECK decides the rest (answered `too_large`).

Measured with PostgreSQL itself (`model.test.ts`):

| Fixture (`testing.ts`)                                                                                                        | Compact JSON | Stored (`octet_length`) | Fits 65,536 |
| ----------------------------------------------------------------------------------------------------------------------------- | ------------ | ----------------------- | ----------- |
| Realistic largest: every property of every section, all 7 components, all 32 levels, 12-level custom numbering at max lengths | 26,171       | 28,802                  | Yes         |
| Adversarial largest: the same, numbers at 17 significant digits, numbering text in 4-byte characters                          | 29,749       | 32,380                  | Yes         |

So no snapshot the schema admits reaches the limit today. The tests do not assume it: each fixture is held to whatever its measured size says. The too-large paths are tested with a smaller injected limit (`prepareAppearance(…, limit)`, tests only) and with a direct oversized insert that the CHECK refuses and `constraintOutcome` maps.

**Names.** Trimmed; 1–80 characters counted as code points (as `char_length` counts); no control characters or line/paragraph separators; case kept. Uniqueness ignores case only as PostgreSQL's `lower()` does. There is no accent or other folding.

| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `accountDefaultOf(user)` / `getAppearanceDefault()`                                                   | The default from the request's own account row: no query                                                                                                            |
| `setAccountDefault` / `setAppearanceDefault({ target, expectedRevision })`                            | Built-in or own personal preset. `updated`, `unchanged`, `conflict` (with the current default), `not_found`                                                         |

| `resolveAccountDefault(db, owner)`                                                                    | For A4.2C: the built-in id, or the personal preset's validated snapshot to copy (`unreadable` if it no longer parses). One query                                    |
| `reconcile.ts`: `settledRename`, `settledReplace`, `settledDelete`                                    | After an answer that never came: what a fresh `get` proves (`applied`, `not_applied`, `superseded`)                                                                 |

Action results are `ActionResult & { code?, … }` with snake_case codes:

`unauthorized`, `invalid`, `too_large`, `not_found`, `unreadable`, `conflict`, `duplicate_name`, `limit_reached`, `operation_reused`, `account_unavailable`, `failed`

Messages come from the new `appearancePresets` dictionary, in English and Spanish ("estilo predefinido", as the editor already says).

- Every action calls `authorize("active")`, takes the owner from the session, and parses its whole input with a strict schema (an `ownerId` is refused) before any database work.
- Nothing is revalidated, since no page shows presets yet.
- Failures are logged with `failure()` (kind and SQLSTATE only). Never `describeDatabaseError`, which would log the name and appearance from Drizzle's parameters (tested).

## Revisions, locks, and transactions

- **Lock order.**
  - Every change runs in one transaction that locks the account's row first (`SELECT … FROM users … FOR NO KEY UPDATE`).
  - It then rechecks `status = 'active'` and setup with the row held, answering `account_unavailable` otherwise.
  - Then, where it needs one, it locks the preset's row (`FOR UPDATE`, or `FOR KEY SHARE` to choose it as the default).
  - That order is the same everywhere. Reads take no lock.
- **Revisions.**
  - Compared with the rows held.
  - Every `UPDATE` and `DELETE` also carries `revision = <expected>` in its WHERE clause.
  - A successful change is `revision + 1`. Timestamps are never a concurrency token.
- **No-ops.**
  - A stale revision is `conflict` and writes nothing, even when the value asked for is already there.
  - The value already stored at the revision named is `unchanged` and writes nothing: no `updated_at`, no revision. Appearance equality is `jsonEqual`, so key order is not a difference.
  - The default has its own revision, `appearance_default_revision`.
- **Count limit.** The count is read with the account row held, so parallel creates cannot pass it together. Verified on real connections (below).
- **Constraint failures.**
  - A unique or CHECK violation aborts the transaction.
  - `settle()` maps it (`duplicate_name`, `too_large`) only after `db.transaction` has rolled back, with no statement sent in the failed transaction.
  - A test makes the name index refuse behind the service's own check and asserts nothing but the rollback follows the refused insert.

## Idempotency

- A create or duplicate names a browser-chosen `operationId`. The preset's ID is always made by the server, so a create can never be used to probe or overwrite another account's preset.
- Inside the transaction, with the account held:
  1. Look up `(owner, operationId)` in the ledger.
  2. Same fingerprint and kind: answer `created`, `replayed: true`, with the original ID and the preset as it is now (`null` if deleted since). Never carried out again.
  3. Different fingerprint or kind: `operation_reused`, and nothing changes.
  4. Otherwise: name check, count check, prune this account's records older than 30 days, then insert the preset and its record together.
- **Fingerprint.**
  - SHA-256 of canonical JSON (keys sorted).
  - Create: its kind, trimmed name, and materialized appearance.
  - Duplicate: its kind, lower-cased source ID, and name.
- **Covered:**
  - a lost create or duplicate answer, retried;
  - the same request sent ten times at once (real connections);
  - an operation ID reused for something else;
  - create, then rename or replace, then the old create retried: answered with the renamed/replaced preset, never overwritten;
  - create, then delete, then the old create retried: no resurrection;
  - the same operation ID used by two accounts: independent.
- **Retention is at least 30 days, not exactly.**
  - A record past 30 days is removed only by that account's next create of a new operation, or by account deletion. There is no timer or cron.
  - Until then a retry is still answered from it.
  - After it is gone, the same request is a new create, which can only make a new preset or be refused (tested: refused as a taken name, the old preset byte-for-byte unchanged).
  - It can never alter an existing preset, because a create never names a preset ID.
- **Other changes** (rename, replace, delete, default) are never resent blindly. After an uncertain answer the client reads with `getAppearancePreset` and judges with `reconcile.ts`. A stale retry is refused by the revision check, never upgraded to a newer revision.

## Account deletion

`processDeletion`'s data transaction now also does three things, after the existing deletes and before the Clerk identity and the `users` row:

1. Sets the account's default back to Balanced (only when it names a personal preset; the `deleting` status is untouched).
2. Deletes its presets.
3. Deletes its operation records.

It is all or nothing, and safe to repeat. No cascade was added.

- Tested in `deletion.test.ts`:
  - an account with two presets, one of them its default, and a record is deleted completely, and another account's are kept;
  - a failure injected into the preset step leaves everything (default included) in place and `retry`, and the next attempt finishes;
  - a create after `requestDeletion` is refused.
- On real connections: a create already holding the account row finishes before `requestDeletion` takes it, and its preset is then removed by `processDeletion`; a create that waits on a deletion request's lock is refused once it commits.

**The race harness** was kept out of the repository:

- Setup: `embedded-postgres` and `pg` were installed into the session's scratchpad. A Vitest global setup started a fresh cluster on port 54329 (`persistent: false`), the committed migrations were applied with Drizzle's node-postgres migrator, and the real services ran through a `pg.Pool` of 30 connections.
- After each run: the cluster was stopped, its data directory deleted, and no `postgres.exe` process remained.
- No shared database was touched.
- Every race test asserts the committed rows afterwards:
  - 95 presets plus 20 parallel creates: exactly 5 `created`, 15 `limit_reached`, 100 presets and 5 ledger rows at the end;
  - 10 parallel creates of one name (mixed case): 1 created, 9 `duplicate_name`, 1 row;
  - one create sent 10 times at once: one preset, one non-replayed answer, all answers the same ID;
  - one duplicate sent 10 times at once: one copy;
  - 10 renames at one revision: 1 `updated`, 9 `conflict`, revision 2;
  - choosing a preset as the default while deleting it, 25 rounds: the preset gone, the account on Balanced, the default revision 3 or 1 according to which went first;
  - two deletes of the default at once: one `deleted` (reset once, revision 3), one `not_found`;
  - 10 default changes at one revision: 1 `updated`, revision 2;
  - 30 mixed changes on one account at once: no error, no deadlock, exactly one default, a personal default that exists and is the account's;
  - 10 creates racing `requestDeletion`, then `processDeletion`: nothing left (in this run all 10 creates won the lock first);
  - deterministic interleavings with a transaction held open on a raw connection:
    - a create waiting behind an uncommitted deletion request is refused;
    - a deletion request waiting behind a create in progress lets it finish, then `processDeletion` removes it;
    - choosing a preset as the default while its delete is uncommitted waits, then answers `not_found` with the default unchanged.

## For A4.2C

- Read with `listAppearancePresets` (metadata) and `getAppearancePreset` (the snapshot).
- Save the preview's snapshot with `createAppearancePreset`, from `snapshotAppearance(mergeStyles(stored, draft), numbering, fallback)`.
- Rename, replace, duplicate, and delete through their actions. Delete asks for confirmation first, and says so when `defaultReset`.
- Choose the default with `setAppearanceDefault`.
- Generate one `operationId` per create or duplicate intent, and keep it until an answer comes. Resend with the same ID on a lost answer; never mint a new one for a retry. For everything else, re-read and use `reconcile.ts`.
- **Apply** a preset only through `snapshotDraft(snapshot, styles, doc, draft)` into the Appearance session, then the existing Apply. Never write `doc.attrs.styles` or `layout` directly.
- **New outlines:** copy `resolveAccountDefault`'s result into the new document's styles and numbering explicitly. An `unreadable` personal default needs a decision (offer Balanced, never silently).
- **Offline:** show that presets need a connection. Do not queue.
- **Not built:** any of the above UI, and new-outline initialization.

## Remaining risks

- **Neon has not run these locks.** The race behaviour was proven on PostgreSQL 18.6, not on Neon's pooler. The transactions are interactive on one pooled WebSocket connection each, as the rest of the application's are.
- **Retention is opportunistic.** An account that never creates again keeps its old operation records until it is deleted. They are tiny and bounded by how many creates it ever made.
- **A retry later than the retention window** of an operation whose record was pruned is treated as new. It can only create (or be refused), never change an existing preset.
- **Rollback after presets exist** blocks account deletion on the older build until A4.2B's code is back (documented, safe, recoverable).
- **Reads are Server Actions.** Next.js runs a client's actions one at a time, so a list or get waits behind any pending action from that tab. Harmless for presets today, since nothing autosaves them. A4.2C may move reads to a route if that ever matters.

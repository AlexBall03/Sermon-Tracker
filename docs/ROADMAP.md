## Phase 3 — Outline System

After Phase 2E and Phase 2F, in that order. Implemented (3A to 3C).

An outline holds the general shape of a sermon a person is thinking of preaching: short headings, brief notes, passages, and points under points. The sermon itself is written elsewhere. This is an outline organizer, not a place to write a manuscript.

- **3A: Outline foundation** — implemented ([handoff](HANDOFF-3A.md)). Three tables (`sermon_outlines`, `outline_entries`, `outline_entry_scripture_references`), each tied to its owner by the database; one outline to a sermon, made only for a sermon that exists; points nested to any depth, with an optional introduction and conclusion, one of each; ordering that is always whole, with a point moved together with everything under it and never under itself; numbering worked out when shown and never stored, in seven built-in styles and custom ones; an entry made from a saved point idea as a copy that remembers its source and survives the point's deletion; passages on an entry as numbers; stale changes detected, the shape and the words apart; owner-checked actions that say what each change left behind. Migration `0013`, applied to development only. No interface. Checked with type checking, lint and formatting on the files changed, its own unit and database tests with the existing ones it touches, a one-off run against the development database on concurrent connections, and a production build; the whole unit suite and the end-to-end suite were not run
- **3B: Structured outline editor** — implemented ([handoff](HANDOFF-3B.md)). No migration and no new package. `/outlines/<id>` is the editor and `/outlines/new?sermon=<id>` the way in until 3C links to it. Checked with unit, component, and page tests, a production build, and a signed-in end-to-end journey at desktop and phone widths. The editor at phone and desktop widths; adding, editing, and removing entries; the introduction and conclusion; nesting, with drag and drop and controls that do the same without it; collapsing and expanding; autosave with a visible save state; choosing and customizing the numbering
- **3C: Sermon, library, and Bible integration** — implemented ([handoff](HANDOFF-3C.md)). No migration and no new package. Outlines in the main navigation, at `/outlines`: an overview of the outlines of active sermons, searched by sermon title, ordered by when they were worked on, by title, or by when they were made, a page at a time. Making an outline for an existing sermon or for one captured on the spot, never twice for one sermon and never by opening a page; "Open Outline" or "Create Outline" on a sermon's page and its card in Sermon Ideas; the sermon's delete confirmation says its outline goes too. In the editor: "Add from Saved Point", a copy of a point idea's heading, notes, and passages that remembers its source and never changes it; passages on an entry, read in place, bounded when long, and opened in the Bible with the way back to the outline. **Decided here: meaningful outline work is developing the sermon** and moves its `last_developed_at` (an empty point, a move to the same place, numbering, and making or deleting an outline do not). Creating a point idea from an entry is not built
- **3D: Preview, print, and hardening** — withdrawn as a phase on 13 October 2026; never started. Its accessibility, narrow-screen, and release checks belong to whichever phase changes the thing checked, and are not gathered into a hardening phase. An outline preview and a printer-friendly layout are not built and are not scheduled; if they are wanted they will be planned as a feature of their own

## Release strategy and phase rules

- **Order (revised 16 October 2026):** 5D.2 ✅ → 6A ✅ → Private Beta Release Candidate Check (formerly 6B) ✅ (owner-reported) → private beta ✅ (invitations sent) → Condensed Public Release (checkpoints 1–4 implemented) → **owner production configuration and smoke tests (next)** → public release → 9.
- Maintain proportionate tests, accessibility, responsive behavior, handoffs and architectural constraints **inside each implementation phase**. Release gates validate the whole system.
- Protect user content: never silently discard queued offline work; preserve server authorization and ownership. Neon remains authoritative; IndexedDB is per-device storage.
- Phase 7 ordering can respond to beta evidence. A feature that is unnecessary to ship safely should not block users from benefiting from the core product.
- Broad public rollout depends on verified product quality, operational readiness and truthful feature documentation, **not** simply finishing an arbitrary number of features.

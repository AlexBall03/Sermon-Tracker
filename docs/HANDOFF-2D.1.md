# Phase 2D.1 Handoff — Classification Architecture & Data Model

Written 12 October 2026. [ARCHITECTURE.md](../ARCHITECTURE.md) is the technical reference (see "Classification"); [DATABASE.md](DATABASE.md) has the columns and the migration ("Phase 2D.1 migration"); this is the summary.

## A. What was implemented

The data layer for classifying an idea, and no new interface.

- **Development status**: `idea`, `developing`, `ready`, `on_hold`. A new idea is `idea`. Changed by hand only; any status may follow any other.
- **Intended format**: `full_length`, `mini`, `flexible`, `unspecified`. A new idea is `unspecified`.
- **Sermon type**: `topical`, `textual`, `expository`, `unspecified`. A new idea is `unspecified`.
- **Archiving**: `archived_at`, a date or null, apart from all three. `archiveIdea` and `restoreIdea` change it and nothing else.
- **Words for all of it** in English and Spanish: a label and a meaning for every status and format, and a label, definition, and example for every sermon type, returned as lists by `classificationOptions(locale)`.
- **Saves no longer reset a classification.** `updateIdea` now parses with `ideaUpdate`, where a classification left out is left alone.
- **Three new actions**, each authorising itself and scoped to the owner: `classifyIdea`, `archiveIdea`, `restoreIdea`.

## B. How the brief met the repository

- **Ideas are one table** (`ideas`, told apart by `kind`), so the classifications are columns on every idea. Format and type are a sermon's: like `subject`, they are kept when an idea is reclassified, and shown and filtered on sermons only. Any idea can be archived.
- **`status` already existed** as `captured | developing | ready`, and **`sermon_type`** as a nullable `topical | expository`. `captured` is now `idea` and null is now `unspecified`. The TypeScript name stays `status`; the brief's `developmentStatus` is the same thing.
- **The table still admits `captured` and null.** Production migrates during the build, under the previous deployment, which writes both on every save and refuses the new values. So 0007 only adds and widens, no row is rewritten, and the new code reads the old values as the new ones in one function (`asRead`, `features/ideas/ideas.ts`). Agreed with the owner; the alternatives were a second `development_status` column, or rewriting in place and breaking saves while a build runs.
- **Sermon-to-point links do not exist.** The brief speaks of reusable points associated with several sermons; no such table has been built (it was listed as 2C.3, not started). There was nothing to preserve and nothing to test. A point is its own `ideas` row and is untouched by any of this.
- **Phase numbers.** The roadmap was renumbered to the brief's order (2D, 2E preaching history, 3 outlines, 4 onboarding, 5 PWA). What were Phases 5, 6, and 8 (insights, sharing, launch readiness) have no number in the new order and are listed as "Later" until the owner places them.

## C. Database

One migration, `0007_idea_classification`, generated by `npm run db:generate`:

- `ADD COLUMN intended_format text DEFAULT 'unspecified' NOT NULL`, with a CHECK.
- `ADD COLUMN archived_at timestamptz`.
- `status`: default `idea`; CHECK now `idea`, `developing`, `ready`, `on_hold`, and still `captured`.
- `sermon_type`: default `unspecified`; CHECK now `topical`, `textual`, `expository`, `unspecified`, and still null.

No `UPDATE`, nothing dropped but the two CHECKs it widens, no `NOT NULL` added to an existing column.

- **Applied to the development database** with `npm run db:migrate:dev` (declared and stamped `development`): 8 applied, 0 pending. **No production or preview command was run.**
- **Production** applies it by itself in the next production build, as every migration does. Nothing to do by hand.
- **Still owed: the tightening migration.** After this release is live, rewrite `captured` to `idea` and null to `unspecified`, drop both allowances from the CHECKs, and make `sermon_type` NOT NULL. The SQL and the rule for it are in DATABASE.md. It must not ship in the same release as 0007.

## E. What changed on screen

Nothing was designed, but three existing controls list their choices from the model, so they changed with it (agreed with the owner):

- The status choice in the editor and in quick capture's "More details" now reads Idea, Developing, Ready, On Hold. "Captured" became "Idea".
- The sermon-type choice now reads Topical, Textual, Expository, Not Specified, in that order; "Not set" was first and is now the last value.
- The library's status and sermon-type filters offer the same values.

**These were not looked at in a browser.** Four options in a control that held three may wrap or crowd on a narrow screen; 2D.2 replaces these controls and should check.

Intended format and archiving have no control anywhere.

## G. Outstanding

- **The tightening migration** (section C).
- **The changed controls need a look** on a narrow screen (section E).
- **The Spanish wording is mine**, not a native speaker's: the meanings, the definitions, and the examples, including the title given for 1 Samuel 17:29 ("¿No hay una causa?"), which should be checked against the RVG's own words.
- **Archived ideas are still listed everywhere.** Nothing can archive from the interface yet, so nothing is hidden yet. Whoever builds the archive control decides where archived ideas are shown and adds the filter.
- **A save still replaces content whole.** `updateIdea` leaves an unnamed classification alone, but `kind`, `notes`, `subject`, and `references` are still written from the input as before; the editor always sends them all.
- **Offline (Phase 5).** Idea IDs can already be made in the browser and creation is idempotent. Classification values need no server to check. Nothing was built for it.

## I. Ready for 2D.2

Ready. What the interface can use as it stands:

- **Types and lists** (`features/ideas/model.ts`, no server code): `ideaStatuses`, `intendedFormats`, `sermonTypes`; `IdeaStatus`, `IntendedFormat`, `SermonType`; `classificationDefaults`.
- **Options to render** (`classification.ts`): `classificationOptions(locale)` gives `statuses` and `formats` as `{ value, label, meaning }` and `sermonTypes` as `{ value, label, definition, example }`. In a Client Component, call it with `useLocale()`.
- **Validation** (`schemas.ts`): `ideaSchemas(locale).ideaInput` for a new idea, `.ideaUpdate` for a save, `classificationInputSchema` for a change. `IdeaDraft` already holds `status`, `intendedFormat`, and `sermonType`.
- **Actions** (`actions.ts`): `classifyIdea(id, { status?, intendedFormat?, sermonType? })`, `archiveIdea(id)`, `restoreIdea(id)`, each answering `{ ok, message }` in the account's language; `createIdea` and `updateIdea` take all three classifications.
- **Reads**: every idea from `getIdea`, `recentIdeas`, and `searchIdeas` carries `status`, `intendedFormat`, `sermonType`, and `archivedAt`.

Not there, and 2D.2's or 2D.3's to add: a library filter or URL parameter for format or for archived ideas; `IdeaMatch` (the picker's answer) does not carry format or archive state.

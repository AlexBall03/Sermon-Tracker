# Handoff: Phase 5A, the installable application

14 October 2026. Phase 5A makes Sermon Tracker an installable Progressive Web App on iOS, Android, Windows, and macOS, with a service worker that is safe to build offline work on later. **It does not work offline.** The installed application still needs a connection for everything but a page saying so. No migration. No new package.

The technical description is "Installed application" in `ARCHITECTURE.md`; this file says what was done, why, and what was checked.

## 1. What was built

- **A web app manifest** (`src/app/manifest.ts`, served at `/manifest.webmanifest`): name, description, `id` and `start_url` `/dashboard`, `scope: "/"`, `display: "standalone"`, light-canvas colors, two standard and two maskable icons.
- **Maskable icons** (`public/brand/icon-maskable-192.png`, `-512.png`), made by the existing brand script from `mark.svg`: the full-bleed tile with the book at 80% so no mask clips it. The existing icons were regenerated byte for byte the same.
- **iOS metadata** (`appleWebApp` in the root layout) and a `theme-color` that follows the theme in force, a manual choice included.
- **A service worker** (`src/features/pwa/service-worker.ts`, served by `src/app/sw.js/route.ts`), registered in production builds only. It keeps the offline page and public static files, and nothing of any account.
- **An offline page** (`/offline`) shown in place of a page the network could not reach: in the device's last interface language, with Try again and an automatic retry when the connection returns.
- **"Install the app" in Settings**, Appearance & Experience: a real install button where the browser offers its prompt, and otherwise the steps for iOS and iPadOS, Safari on a Mac, Android, Chrome or Edge on a computer, an unsupported browser, or general directions. Running installed, it says so and offers nothing.
- **Updates**: a new deployment's worker waits; a notice above the tab bar offers Update or Later. Update is refused while anything is unsaved, and otherwise reloads that tab once.
- **Signed-in use only** (the owner's rule, given while this phase was planned): the installed application opens on sign-in or the dashboard and never shows the public page.
- **The landing page's Mobile App copy** made accurate: platform-specific steps, "sign in if it asks" instead of "you stay signed in" (iOS keeps the installed app's sign-in apart from Safari's), a connection is needed, and Settings has the steps. Text only; nothing was redrawn.

## 3. How installing works

`startPwa()` (`pwa.ts`) runs once from `PwaRuntime` in the root layout. It keeps the browser's `beforeinstallprompt` from whatever page it fires on (it fires once, early) so the Settings button can use it later, notes `appinstalled`, and registers the worker after `load`. State lives outside React and is read with `usePwa()`.

`installGuide()` (`install.ts`, pure) chooses what Settings shows. The user agent is read only to choose which steps to describe; a missing prompt is never taken to mean "not installable" or "installed". "Installed" means this window is the installed one (`display-mode` standalone, minimal-ui, or window-controls-overlay, or iOS's `navigator.standalone`). Browser full screen (F11) is deliberately not counted.

There is no banner and no prompt anywhere but Settings, so nothing promotes installing to someone who has installed.

_Changed 14 October 2026 at the owner's request:_ the dashboard also shows a dismissible `InstallNotice` card once the tour invitation has been answered. It is hidden in the installed window and once this browser dismisses it or installs from it. See "Installed application" in `ARCHITECTURE.md`.

## 4. The service worker

Hand-written, about 200 lines of plain script, no Serwist: the policy is an allowlist small enough to read in full, and Serwist would add a build plugin and defaults that would need overriding. `service-worker.test.ts` runs the real script in `node:vm`.

| Request                                                                                                             | What happens                                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A page (navigation)                                                                                                 | Network, with navigation preload. Never stored. Only a network failure (the fetch rejects) gets the kept `/offline`; every answer from the server, a redirect to sign-in or a 500 included, is passed on unchanged |
| `/_next/static/…`                                                                                                   | Cache first; stored only if `ok` and same-origin; query ignored when matching                                                                                                                                      |
| `/brand/…`, `/icon.svg`, `/apple-icon.png`, `/manifest.webmanifest`                                                 | Kept copy, refreshed in the background                                                                                                                                                                             |
| `RSC` / `Next-Action` / `Next-Router-*` headers, `_rsc`, `/api`, `/__clerk`, `/_next/image`, other origins, non-GET | Not answered at all                                                                                                                                                                                                |

Installing fetches `/offline` with `credentials: "omit"` and `cache: "no-store"`, then the static files its HTML names (scripts, styles, and the chunks listed in its payload) and the fonts its CSS names. One cache per version (`st-<version>`); activation deletes older `st-` caches and claims open pages. The version is `APP_VERSION`, set in `next.config.ts` from `VERCEL_DEPLOYMENT_ID`, then `VERCEL_GIT_COMMIT_SHA`, then a local build time, and written into the script, so each deployment is a new script and the browser's own update check finds it. `/sw.js` is served `no-cache, no-store`. The proxy does not run for it (its matcher skips `.js`).

## 5. Manifest and icons

- `start_url` and `id` `/dashboard`: see section 6. `scope` `/`, so the sign-in page and Clerk's return stay inside the app window.
- `background_color` and `theme_color` `#f7f5f0`, the light canvas and the default theme. A manifest cannot carry a dark variant; the page corrects `theme-color` as soon as it loads (`PwaRuntime`, read from the page's own computed background, so no color is written in a component).
- `display_override: ["standalone", "minimal-ui"]`. No shortcuts: their labels could only be English.
- Maskable icons: full-bleed tile, book scaled to 80% about the center (the original's corners reach about 41 units from the center; the safe circle is 40). The ribbon stays at the top of the left page.
- iOS uses `apple-icon.png` (already full bleed). No iOS startup images were made: about forty device-specific images would be needed. iOS shows a plain screen briefly, then the existing splash.

## 6. Authentication and routing

No access code changed.

- Launch signed out: `/dashboard` → the proxy's `redirectToSignIn` with the dashboard as the return address → `/sign-in`. `/` is never requested (an end-to-end test checks this).
- Launch signed in: the dashboard; an account that owes setup is sent to `/onboarding` by `requireActiveUser()`, as in a browser. No loop: the setup page asks for an account, not a finished one.
- The installed window never shows `/`. `LeavePublicPage` in the `(marketing)` layout replaces the address with `/sign-in` (an inline script before paint, and a layout effect for a move inside the app); sign-out from the installed window goes to `/sign-in`; the auth shell hides its logo link and "Back to home" with the `standalone:` CSS variant. A signed-in person reaching `/sign-in` is sent to the dashboard by the proxy as before.
- On iOS the home-screen app keeps its own cookies, so a first launch asks for sign-in even if Safari is signed in. The Settings block and the landing copy say so.

## 7. Cache security rules

- No navigation response is ever stored. The only HTML kept is `/offline`, fetched without credentials.
- No Server Component payload, Server Action, route handler, Clerk request, image optimizer response, or cross-origin response is answered or stored.
- Only `ok`, same-origin responses are stored.
- Cache names start `st-`; a future per-account store must use IndexedDB (5B) with the account in its key, never this cache.
- Installing grants nothing: every page still goes to the server, which decides access as before.

## 8. Standalone behavior

Nothing in the navigation, header, or tab bar changed. What existed already covers it: `viewportFit: "cover"`, the tab bar's `safe-area-inset-bottom` padding, `container-page`'s left and right insets for a notch in landscape, and the dialogs' top and bottom insets. iOS's status bar is `default`, so content is never drawn under it and the fixed bar needs no top inset. Same-origin links stay in the window; Clerk's own redirects are within scope.

The splash screen, its timing, the Clerk sign-in fix, and the progress bar are untouched. `PwaRuntime` draws nothing. The offline page carries the splash's script harmlessly (no cookie, so no splash).

## 9. Updates

1. A deployment changes `/sw.js`. The browser installs the new worker; it waits (no automatic `skipWaiting`).
2. `pwa.ts` sees a worker reach `installed` while another controls the page and sets `updateReady`. The very first worker on a device controls nothing yet and is not treated as an update.
3. `UpdateNotice` (in the `(app)` shell only) shows "A new version of Sermon Tracker is ready." with Later and Update. It is a status region and never takes focus.
4. Update calls `applyUpdate()`: refused with an explanation while `hasUnsavedWork()`; otherwise it posts `SKIP_WAITING` and reloads that tab once when the new worker takes over. Other tabs are not reloaded.
5. Later hides the notice for that page; a waiting worker takes over by itself when every window is closed.
6. A window shown again checks for an update at most every 30 minutes, for an installed window kept open.

`src/lib/unsaved-work.ts` is held by `useLeaveGuard` while dirty (the idea editor, quick capture) and by the outline store while its status is not `saved`, including after the editor page is gone, which `beforeunload` alone did not cover. The browser's own `beforeunload` warnings remain a second barrier.

**Limitation:** forms that do not use `useLeaveGuard` (the Settings profile fields, the setup wizard's fields, the preaching and outline dialogs) hold nothing. The notice is not shown in the setup shell. Inside the application, a modal dialog makes the notice unreachable while open, so a half-filled dialog cannot be reloaded over from the notice; a form typed into outside a dialog and outside the leave guard could be. Phase 5C, which needs a full account of pending work anyway, is where to close this.

## 10. Languages

All new words are the `pwa` dictionary, English and Spanish, read with `useT` / `getT` / `dictionary`. The offline page cannot ask the server, so it reads `st-locale`, written by `I18nProvider` with the language in force (the administrator's Spanish switch already applied), falling back to the browser's language; it draws nothing until it has chosen, so no English flashes for a Spanish reader. The manifest is in English only (one language per manifest; only its name and description show, and the name is the same in both). The offline page's server-side `<title>` is English and is replaced as soon as the page knows its language.

## 12. Known limitations

- Nothing works offline but the offline page. Pages visited before are not kept, by design (they are an account's).
- No iOS startup images.
- The update coordination covers the leave guard and the outline store only (section 9).
- A browser that never fires `beforeinstallprompt` (Safari, Firefox) always gets instructions, never a button.
- The manifest's colors are the light theme's; an installed app opening in dark mode on Android shows a light system splash before the page.
- The update notice and a toast share the foot of the screen and can overlap for the toast's six seconds.

## 14. Dependencies

None added. Serwist, which Next's PWA guide points to, was considered and not taken (section 4).

## 15. What Phase 5B can build on

- `PwaRuntime` / `startPwa` as the one place the worker is registered, and `usePwa()` for state.
- The worker's `message` handler (`SKIP_WAITING`, `GET_VERSION`) for new messages; its allowlist for any new route (each must be argued in).
- `st-<version>` is the worker's static cache only. Downloaded Bible text and account data belong in IndexedDB, keyed by account, with a local-access policy designed in 5B; the worker must never answer a page from them without that policy.
- `src/lib/unsaved-work.ts` as the start of an account of pending work for 5C's queue.
- `st-locale` for any page that must speak before the server answers.
- `experimental.useOffline` (Next's retry of navigations and Server Actions) is a 5C decision: it changes what an action does offline.

## 16. Open risks

- **The offline page's static files are found by reading its HTML.** If a future Next changes how chunk paths appear in the page, installing fails loudly (the worker does not install, and the site keeps working without it) rather than silently. `service-worker.test.ts` covers the current shapes; the end-to-end spec covers the real build.
- **Clerk on the offline page.** Clerk's script cannot load offline. The page does not need it and rendered and passed its tests offline, but the browser console was not inspected for Clerk's messages, and Clerk offline in an installed window has not been seen on a device.
- **Update detection in a window left open** relies on `visibilitychange` and the browser's own checks; a window kept in front for days without being hidden only learns of an update on its next navigation that reaches the server.

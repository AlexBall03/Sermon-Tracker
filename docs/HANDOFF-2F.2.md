# Handoff: Phase 2F.2 — Related ideas

12 October 2026. One migration (`0011_related_ideas`), two new tables, no new package. **Status: implemented; targeted tests, type checking, lint, formatting, and a production build pass; the whole unit suite and the end-to-end suite were not run, and nothing was seen in a signed-in browser (section 8).** Migration applied to development only. Not deployed.

## 1. What was implemented

- Relating two sermon ideas. The relation has no direction: made from either sermon, it is seen from both, and it is stored once.
- Relating a reusable point idea to a sermon. One point can go with any number of sermons and stays one record.
- A **Related Ideas** section on an idea's page, with a searchable picker for adding and a button for removing.
- Archived ideas shown and offered there, marked "Archived".

Nothing of Phase 2F.3 or Phase 3 was built. No navigation item, page, library filter, setting, suggestion, or score was added.

## 2. A corrected assumption

The brief for this phase said to reuse the existing sermon-to-point relationship. There was none: no table, no service, no interface, and the roadmap listed "sermon-point associations" as unstarted Phase 3 work. The owner decided, on 12 October 2026:

- to build the plain association here, with no order and nothing written for one sermon;
- that Phase 3's outline entries will be a separate table that names a point directly, with no need for a row here first;
- that archived ideas stay visible and selectable in Related Ideas, as a deliberate exception to the library's rule.

`ARCHITECTURE.md` ("Domain decisions") and the roadmap's Phase 3 list were reworded to match.

## 3. Data model

| Table              | Columns                                                | Rules                                                                                |
| ------------------ | ------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `sermon_relations` | `sermon_a_id`, `sermon_b_id`, `owner_id`, `created_at` | Primary key on the pair; `CHECK (sermon_a_id < sermon_b_id)`; index on `sermon_b_id` |
| `sermon_points`    | `sermon_id`, `point_id`, `owner_id`, `created_at`      | Primary key on the pair; `CHECK (sermon_id <> point_id)`; index on `point_id`        |

- **One row per pair of sermons.** The lower ID is always `sermon_a_id`. The CHECK refuses a sermon with itself and a pair written the other way round; the primary key refuses the same pair twice. A sermon's relations are read from both columns.
- **Ownership is in the keys.** Each foreign key is `(idea, owner_id)` → `ideas (id, owner_id)`, as in `idea_tags`, so one account's idea cannot be related to another's whatever the application does.
- **`ON DELETE CASCADE`.** Deleting an idea removes its relations and leaves the other idea alone. A preached sermon still cannot be deleted (unchanged).
- **Kinds are the service's to check.** A foreign key cannot say an idea is a sermon. `linkIdeas` reads both rows `FOR UPDATE`, lower ID first, and checks.

The migration was generated by `npm run db:generate` and renamed to `0011_related_ideas` (the `.sql` file and its `tag` in `drizzle/meta/_journal.json`) before it was applied anywhere; its SQL was not edited. It creates two tables and alters nothing, so it is safe under the code now live and after a rollback.

## 4. Service and actions

`src/features/ideas/relations.ts` is the only code that touches either table. Every statement has the owner in its WHERE clause.

| Function                              | What it does                                                                                                                                                                  |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `relatedIdeas(db, owner, id)`         | `{ sermons, points }` for a page, by title. A sermon gets both; a point gets the sermons it goes with; an undecided, unknown, or foreign idea gets nothing                    |
| `linkIdeas(db, owner, id, otherId)`   | `linked`, `already`, `missing`, `self`, or `kinds`. Two sermons go to `sermon_relations`; a sermon and a point, in either order, to `sermon_points`; anything else is `kinds` |
| `unlinkIdeas(db, owner, id, otherId)` | Removes the pair from whichever table holds it, whichever way round it is named. Nothing there is not an error                                                                |

- **Duplicates.** The insert is `ON CONFLICT DO NOTHING`, so a repeat, the reverse, and several requests at once leave one row; all but the first answer `already`.
- **Refiled ideas.** A relation is kept when one of its ideas is filed as something else, and left out by `relatedIdeas`, which matches on the current kind. Filed back, it is shown again.
- **Actions** `relateIdeas` and `unrelateIdeas` (`relation-actions.ts`) authorize themselves, parse both IDs, take the owner from the session, and answer "That idea no longer exists." alike for an idea that is missing and one that is someone else's.

## 5. What relating does not do

Nothing in `relations.ts` writes to `ideas`. So, on both sides of a relation, for sermons and points alike:

| Column              | Relating | Unrelating |
| ------------------- | -------- | ---------- |
| `last_developed_at` | Unmoved  | Unmoved    |
| `updated_at`        | Unmoved  | Unmoved    |
| `status`            | Unmoved  | Unmoved    |
| `archived_at`       | Unmoved  | Unmoved    |

The Phase 2F.1 rule is as it was: only `updateIdea` (title, subject, notes, or passages changed) and `attachReferences` (a passage added) set `last_developed_at`. `needsAttention` and `revisitIdeas` were not changed, and nothing was backfilled.

## 6. Interface

On an idea's page (`/library/<id>`), between the form and the preaching record, outside the draft:

| Idea      | What is shown                                                 |
| --------- | ------------------------------------------------------------- |
| Sermon    | Related Sermons and Related Points, each with an "Add" button |
| Point     | Related Sermons: the sermons it goes with, with "Add sermon"  |
| Undecided | Nothing. The section is not drawn                             |

- **A row** is the idea's title as a link, its status, an "Archived" badge where it applies, and a remove button named for the idea ("Remove Faith from related ideas"). The link carries the page's `from`, so "Back to Sermon Ideas" still returns to the library as it was left.
- **Removing** is not confirmed: it loses nothing, and the idea can be added again. The row goes at once, comes back with the reason if the server refuses, and the page is read again on success.
- **The picker** (`RelateIdea`) is a dialog like "Add to an idea": a search box, the ideas changed most recently before anything is typed, a skeleton while loading, a line when nothing matches, a retry when the search fails. It searches what the library searches (title, notes, a sermon's subject) among sermons or among points. The idea on the page is never offered; one related already is shown as "Related" and disabled; an archived one is badged. It stays open so several can be added, and closes with Done.
- **Shared search.** The picker and `AttachScripture` use one hook, `useIdeaSearch`, lifted out of `AttachScripture`, whose behavior is unchanged. `/api/ideas/search` now also reads the library's `archived` parameter and returns `archived` on each match; without the parameter it never offers an archived idea, as before.
- **New points** are still made with quick capture. No second way to create one was added.

## 7. Localization

English and Spanish, in the existing `ideas` dictionary: `related.*` (headings, buttons, empty states, the picker) and seven `actions.*` messages. The picker reuses `attach.*` for what the two dialogs say alike, and `statuses` and `archived` are the existing words. The Spanish wording is the agent's and was not seen on screen.

What the tests show, the database ones against an in-memory PostgreSQL running the committed migrations:

- A relation made from either sermon is seen from both and is one row; a repeat, the reverse, an upper-case ID, and three requests at once leave one row; a sermon is never related to itself.
- Removing a relation leaves both sermons and every other relation; removing one that is not there is safe.
- One point related to two sermons, from either side, is one point; unrelating it from one keeps it and its other sermon.
- Point with point, and anything with an undecided idea, is refused.
- Another account's idea is `missing`, cannot be read, and its relations cannot be removed; the tables themselves refuse a self-relation, a reversed pair, a duplicate, and a pair across accounts under either owner.
- Archiving and restoring keep relations; archived ideas are returned and marked; an archived idea can be related and keeps its archive date and status.
- Deleting an idea removes its relations and leaves the other ideas; deleting a point leaves nothing stale.
- A refiled idea's relation is hidden and returns when it is filed back.
- `updated_at` and `last_developed_at` are unchanged on every idea after relating and unrelating; an edit to the notes of a related sermon still sets `last_developed_at`, on that sermon only.
- The actions refuse a signed-out or disabled caller and malformed IDs before the database is touched, and report a database failure without its details.
- The search route offers archived ideas only when asked, and marks them.
- The section: both lists, the empty states, the archived badge, the link with its way back, removal at once with no dialog, a refused or unsent removal put back with its reason, the picker's request, the idea on the page left out, an idea related already disabled, a just-related one disabled, nothing matching, a refusal kept in the dialog, and Spanish.

## 9. Known limitations

- **Not seen in a signed-in browser.** Layout at phone width, the dark theme, and the Spanish strings were not looked at on screen.
- **While this was being built, the owner's running dev server showed "Something went wrong" on an idea's page for about a minute**: the page's new queries were saved before `0011` was applied to development. It was applied; nothing was lost. A deployment cannot do the same, since production migrates during the build, before the new code serves.
- **The picker's count can be one high.** The idea on the page is left out of the list in the browser, so "Showing 8 of 12" may count it.
- **A related idea's row shows its title and status only**, not its subject, passages, or dates.
- **No count of related ideas** on a library card or anywhere else, and no library filter for them. Both were optional in the brief and left out.
- **A relation hidden by refiling cannot be removed until the idea is filed back.** It is harmless and goes with the idea if it is deleted.
- Carried from Phase 2E.2 and unchanged: the end-to-end suite and the signed-in browser pass are outstanding.

## 11. Readiness for Phase 3 and Phase 2F.3

**Phase 3 (outlines).** Ready, with one thing to hold to: outline entries are a new table with their own order, parent, and per-sermon wording, naming a point's idea ID directly. `sermon_points` is not that table and should not grow into it. Whether placing a point in an outline should also relate it to the sermon is a product question for Phase 3; nothing here requires either answer. `useIdeaSearch` and the picker's list are reusable for choosing a point while building an outline.

**Phase 2F.3 (preaching-class preferences).** Nothing here bears on it. Worth settling when it is planned: where the preference is stored (it is an account preference, so beside `users.locale` behind `getPreferences()`), and that it must not infer or write a preaching context, which an account only ever has because it chose one.

## Sermon Tracker project notes

- Read `ARCHITECTURE.md` first; it is the technical source of truth. Current status and next steps: `docs/ROADMAP.md`, `docs/HANDOFF-1B.md`, `docs/HANDOFF-1B.1.md`, `docs/HANDOFF-1B.2.md`, `docs/HANDOFF-1C.1.md`, `docs/HANDOFF-2A.md`, `docs/HANDOFF-2B.1.md`, `docs/HANDOFF-2B.2.md`, `docs/HANDOFF-2C.1A.md`, `docs/HANDOFF-2C.1B.md`, `docs/HANDOFF-2C.1C.md`, `docs/HANDOFF-2C.2.md`, `docs/HANDOFF-2D.1.md`, `docs/HANDOFF-2D.2.md`, `docs/HANDOFF-2D.3.md`, `docs/HANDOFF-2E.1.md`, `docs/HANDOFF-2E.2.md`, `docs/HANDOFF-2F.1.md`, `docs/HANDOFF-2F.2.md`, `docs/HANDOFF-2F.3.md`, `docs/HANDOFF-3A.md`.
- Stay inside the current phase. Do not build later-phase features early.
- The repository owner manages Git. Run read-only Git commands only: no commit, stage, branch, push, pull, or config changes.
- Verify in proportion to the change ("How much to verify" in `ARCHITECTURE.md`): the tests of what changed while building; a production build, the end-to-end journeys that matter, and the whole unit or end-to-end suite only when the change is shared or a release boundary calls for it. Finish a phase's verification inside the phase; do not plan a separate hardening phase for it, and never report a check that was not run.
- Stop every dev, preview, or test server you start before finishing. Never kill processes you did not start.
- The repository is public. No secrets anywhere.
- Use semantic design tokens from `src/app/globals.css`; no hardcoded brand colors in components. The interface is neutral: emerald is for actions, selection, and focus, not for surfaces.
- Schema changes: edit `src/db/schema.ts`, run `npm run db:generate`, commit the SQL. Never `drizzle-kit push`, never hand-edit an applied migration, never run `db:migrate:prod` or `db:stamp`. Production is migrated by its own deployment during `npm run build` (see `docs/DATABASE.md`), so every migration must work with the code already live.
- Every page under `(app)` and every server action checks access itself with the helpers in `src/features/auth/access.ts`. The proxy is routing only.
- `npm run dev` needs a development database. Use `npm run dev:next` when none is configured.
- Idea queries live in `src/features/ideas/ideas.ts` and tag queries in `src/features/ideas/tags.ts`; every one filters by owner in its WHERE clause. Keep it that way.
- The library's search, filters, order, and page are URL parameters. Read and write them only through `src/features/ideas/library-query.ts`; never build a sort or a filter from a raw parameter. Library controls change the address only through `useLibrary().apply` (`src/features/ideas/components/library/library-state.tsx`), which builds each change on the query last asked for and returns to page 1.
- A form that saves an idea's tags must start from the tags the idea already has and send them all back (`draftTagIds`); sending `tagIds: []` by default erases them. A form that leaves `tagIds` out leaves the tags alone.
- Anything that shows, picks, or searches Scripture uses `src/features/scripture`. Bible text and the psalm titles are loaded by the migrate command from `data/bible/kjv.json` and `data/bible/kjv-psalm-titles.json`; never edit either file by hand (see `data/bible/README.md`). A psalm's title is never part of a verse.
- The Bible reader's place is its address. Read and write it only through `src/features/scripture/reader-location.ts`, and move within the reader with `window.history.pushState`, not the router.
- In the Bible reader no selection means no verses, never the whole chapter. Use `src/features/scripture/selection.ts`, and add actions on a selection as children of `SelectionToolbar`. The Scripture Panel (`ScriptureBrowser`) keeps its own rule, where an empty choice is the whole chapter; do not change either to match the other.
- Favorites and highlights are `src/features/scripture/saved`. Every query there filters by owner in its WHERE clause, and every one carries a translation (`translation.id`); keep both. A favorite is its verses and its translation, never its label: do not add a second way to save one that goes round `createFavorite`. A verse has one highlight color; a highlight is never stored on a favorite.
- In the reader, an account's marks are read and changed only through `src/features/scripture/use-chapter-marks.ts`, which shows a change at once and takes it back if the server refuses it. `PassageText` draws a highlight behind the words and a selection across the row; keep them apart, a verse can be both.
- Saved Scripture is a section of the library (`/library/saved-scripture`), reached from `LibrarySections`, and is not in the main navigation. Its search, filters, order, and page are URL parameters read and written only through `src/features/scripture/saved/saved-query.ts`, and its controls change the address only through `useSavedScripture().apply`.
- Scripture reaches an existing idea, from anywhere but its own editor, only through `attachReferences` (`src/features/ideas/ideas.ts`) behind the `attachScripture` action, and only through the `AttachScripture` dialog. It adds and never replaces, and locks the idea's row; do not write `idea_scripture_references` another way. A reference is five numbers and no translation: never store verse text or a translation on one.
- A favorite put on an idea is copied as references. Nothing links the two afterwards; do not add a link.
- The reader's address also carries `through` (the end of a passage pointed out) and `idea` (the idea it was opened from), both through `reader-location.ts` like the rest. `idea` is only ever looked up among the signed-in account's own ideas.
- Every string the interface shows comes from `src/i18n/dictionaries/<en|es>/<feature>.ts`, read with `getT` on the server (`src/i18n/server.ts`) and `useT` in Client Components (`src/i18n/client.tsx`). English defines what exists; add a string to both languages. No new English literal in a component, no second copy of a component per language, and no i18n library. A server component shared with tests takes a `locale` prop instead of calling `getT`.
- The interface language and the Bible translation are two preferences on `users`. Saving a different language sets the translation back to null, so it follows the new language until one is chosen again (`saveLocale`); nothing else writes one from the other, and choosing a translation never writes the language. A new account, and a visitor with no language cookie, start in the browser's language (`deviceLocale`, `src/i18n/device.ts`). What is in force comes only from `getPreferences()` (`src/features/preferences/current.ts`), which applies the administrator's Spanish switch; anything that serves Bible text, lists or writes marks, or chooses a language asks it on the server. Never read `users.locale`, `users.bible_translation`, or `app_settings` around it, and never let the switch rewrite a stored preference.
- Bible text is `scripture_verses` / `scripture_psalm_titles`, by translation (`src/features/scripture/translations.ts`). `bible_verses` and `bible_psalm_titles` are superseded: do not read, load, or drop them outside a migration written for that. `data/bible/rvg.json` is written only by `scripts/bible/build-rvg.mjs` from the publisher's file; never edit it, and never alter the wording. The translation is shown as "RVG", never with a year.
- A reference, a favorite's verses, and the reader's place name no translation: both texts number alike. A favorite or a highlight belongs to the translation it was made in and is never shown in, or copied to, the other; the reader says what was marked in the other (`elsewhere`).
- The reader's translation is `t` and its second pane is `beside`, both through `reader-location.ts`. Change the address with `window.history.pushState`/`replaceState` passing `null` as the state, never `window.history.state`: handed its own state back, Next ignores the call. A pane's translation is shown from the reader's own state at once (`chosen`) and must not wait for the address. Comparing is offered only where the window fits two columns, and the docked navigation steps aside for it; do not bring back a one-pane-at-a-time switch.
- The comparison's scroll lock is `src/features/scripture/scroll-lock.ts`, bound only in `BibleReader`. It is optional, off by default, a browser preference (not in the address), never turns a chapter, and is turned off when either pane's chapter changes. The panes still know nothing of each other.
- An idea's status, intended format, and sermon type are the lists in `src/features/ideas/model.ts`, and their words (labels, meanings, a sermon type's definition and example) are in the `ideas` dictionary, read as lists through `classificationOptions` (`src/features/ideas/classification.ts`). Do not write a value or a label anywhere else, add a definitions table, or let an account add a value.
- A status changes only because a person chose it. Nothing sets one from a date, a note, a tag, a passage, or a sermon being preached, and there is no "preached" status, flag, count, or date on an idea: preaching history will hold that.
- Archiving is `archived_at` and nothing else, through `archiveIdea` and `restoreIdea`. It is never a status, never a delete, and never changes another column, `updated_at` included.
- A save of an existing idea is parsed with `ideaUpdate`, where a classification has no default: one left out is left alone. `ideaInput`, which has the defaults, is for a new idea and for a form that sends the whole draft. A form that saves an idea must carry `intendedFormat` in its draft, as the idea page does.
- Since migration `0008` the `ideas` table holds only the current classification values: `status = 'captured'` and a null `sermon_type`, from before Phase 2D.1, were rewritten to `idea` and `unspecified` and are refused by the table. `asRead` in `src/features/ideas/ideas.ts`, which every idea returned from that file passes through, still reads those two as the new values, as a guard for a database the migration has not reached; never read an idea's row around it, never write either old value, and do not teach it to map anything else. Never hand-edit `0008`: its two `UPDATE`s were added to the generated file before it was applied anywhere.
- An idea's status, format, and type are chosen in `ClassificationSection` (`src/features/ideas/components/classification-section.tsx`) and nowhere else. It only changes the draft. A sermon shows all three; a point or an undecided idea shows its status only, and nothing shows, filters by, or infers a format or a sermon type on one.
- Archived ideas are left out by the query, never by the screen. A list of ideas goes through `searchIdeas` (where `LibraryQuery.archive` is `active` unless the address says otherwise) or `recentIdeas`; a new list of ideas must exclude archived ones the same way. `getIdea` returns an archived idea on purpose, so its address and the Bible reader's way back still work; do not "fix" that.
- Preaching history is `src/features/preaching` (`occurrences.ts`, `venues.ts`, `contexts.ts`). Every query there filters by owner in its WHERE clause, and the tables' foreign keys carry the owner too; keep both. A sermon is one idea however often it is preached: never copy an idea to record another delivery, and never store a count, a date, or a flag about preaching on an idea (`occurrenceCounts` counts when asked).
- Nothing in `src/features/preaching` writes to `ideas`. Recording, changing, or removing an occasion never moves a status, a format, a sermon type, `archived_at`, or `updated_at`. An occasion's `actualFormat` is never copied from the sermon's `intendedFormat`, and nothing is inferred: not the format from the duration, not AM or PM from the venue, the context, or the date.
- An occasion is created only by `createOccurrence`, which checks that the idea is a sermon with the idea's row locked (`FOR UPDATE`); do not insert into `preaching_occurrences` another way, and do not drop the lock. Its ID may come from the browser, and the same ID twice returns the first row unchanged. Do not add a uniqueness rule over sermon and date: a sermon may be preached twice in a day. An occasion stays with its sermon; `updateOccurrence` cannot move it.
- History outlives everything about its sermon. It is kept, and still returned by `searchHistory`, when the sermon is archived or refiled as a point or undecided; do not add an archive or kind filter there. `deleteIdea` returns `"preached"` and deletes nothing when the idea has history, and a venue or context that history names cannot be deleted (`in_use`). The foreign keys are `ON DELETE RESTRICT`; never make one CASCADE or SET NULL.
- A preaching context says what kind of occasion it was, never the weekday or the part of the day: the date and `timeOfDay` say those. The suggested ones are `suggestedContexts` in `src/features/preaching/model.ts`, named in the `preaching` dictionary; do not add a weekday or an AM/PM one, and never create a context for an account that did not pick or write it. What an account names its own context is its business.
- `preached_on` is a calendar date, a `YYYY-MM-DD` string from the form to the table. Never make it a `Date`, convert it between zones, or add a time zone setting; what counts as the future is `latestDateOnEarth` (`src/features/preaching/schemas.ts`). Parse preaching input with `preachingSchemas(locale)`, called per request so today is today. A save of an existing occasion uses `occurrenceUpdate`, where a field left out is left alone and null clears it.
- The library is `/library` (the overview: three cards, no query, no action, no section marked current) and three sections beneath it: `/library/sermon-ideas`, `/library/saved-scripture`, `/library/preaching-record` (`routes` in `src/lib/site.ts`). People see "Preaching Record"; the code keeps `history` and `occurrences`. Never redirect `/library` unconditionally: its page sends on only an address that still carries an ideas query. `/library/scripture` and `/library/history` are old addresses redirected in `next.config.ts`.
- Every section's page starts with `LibrarySectionHeader` (`src/features/ideas/components/library/library-sections.tsx`): "Back to Library", the section's own title, its action if it has one, then `LibrarySections`. Do not rebuild that head on a page, add a second back link, or use browser history for one; a way up is `BackLink` (`src/components/layout/back-link.tsx`) to a fixed address.
- Preaching is recorded through one form, `OccurrenceDialog`, opened by `HistoryProvider` on the Preaching Record and by `RecordPreachingProvider` everywhere else (a sermon's page, a sermon's card, the dashboard). Do not write a second form, and offer the action only for an idea filed as a sermon. The record's search, filters, order, and page are URL parameters read and written only through `src/features/preaching/history-query.ts`, and its controls change the address only through `useHistory().apply`.
- `ideas.last_developed_at` says when an idea's content was last worked on, and is null until that first happens; `updated_at` moves for any write and is not the same thing. It is set only by `updateIdea` when the title, subject, notes, or passages differ from what is stored, and by `attachReferences` when a passage was added. Never set it from a status, format, type, kind, tag, archive, restore, or preaching change, never on create, and never backfill it. Read it as `coalesce(last_developed_at, created_at)`.
- Which ideas are worth revisiting is one rule, `needsAttention` in `src/features/ideas/ideas.ts`, used by the dashboard (`revisitIdeas`) and the library's `revisit` filter: an unfinished sermon (`unfinishedStatuses`) not worked on for `revisitAfterDays` (`src/features/ideas/model.ts`). Do not write a second copy of it, add a setting for the number, pick suggestions at random or by score, or treat a preached sermon as finished. The library's orders sort by `updated_at` and `created_at`, and say "updated".
- Related ideas are `src/features/ideas/relations.ts` and its two tables: `sermon_relations` (two sermons, stored once with the lower ID first) and `sermon_points` (a sermon and a point). Nothing else reads or writes either table. Every query there filters by owner in its WHERE clause, and the tables' foreign keys carry the owner too; keep both. A relation is made only by `linkIdeas`, which checks the two kinds with both rows locked (`FOR UPDATE`, lower ID first); do not drop the lock, the CHECKs, or the canonical order.
- Relating and unrelating never write to `ideas`: not `updated_at`, not `last_developed_at`, not a status, not `archived_at`. Relating an archived idea does not restore it. The keys are `ON DELETE CASCADE`: deleting an idea removes its relations and never the other idea.
- Related Ideas shows and offers archived ideas, marked "Archived". That is the one exception to the rule that a list or picker of ideas leaves them out: `relatedIdeas` has no archive condition on purpose, and the `RelateIdea` picker asks `/api/ideas/search` with `archived=all`. Do not "fix" either, and do not let anything else pass that parameter. A relation whose idea was refiled is kept and hidden (the match is on the current kind), never deleted.
- `sermon_points` says only that a point goes with a sermon. Never add a position, a parent, notes, or wording to it or to `sermon_relations`: those belong to the outline entries (`outline_entries`, Phase 3A), a separate table that names a point directly and does not need a row here. Nothing suggests or creates a relation by itself; relations are chosen in `RelatedIdeas` on an idea's page, and there is no page, navigation item, or library filter for them.
- Outlines are `src/features/outlines` (`outlines.ts`, `entries.ts`) and three tables: `sermon_outlines`, `outline_entries`, `outline_entry_scripture_references`. Nothing else reads or writes them. Every query there filters by owner in its WHERE clause, and the tables' foreign keys carry the owner too; keep both. This is an outline organizer, not a manuscript editor: an entry is a short heading, brief notes, and passages. Do not add rich text, a document model, or an outline status.
- One outline to a sermon, made only by `createOutline`, which checks that the idea is a sermon with the idea's row locked (`FOR UPDATE`); `UNIQUE (sermon_id)` is what makes it one, so never drop it. Nothing in `src/features/outlines` writes to `ideas`: not a status, not `updated_at`, not `last_developed_at`. Deleting a sermon deletes its outline (`ON DELETE CASCADE`); deleting an outline never touches the sermon. `getOutline` returns the outline of an archived or refiled sermon on purpose; `listOutlines` leaves those out.
- An entry is `introduction`, `point`, or `conclusion`, and a point is a point at any depth: never add a type, a depth column, or a stored path for subpoints, and never a limit on depth (`outlineLimits.entries` is the bound). The introduction and the conclusion are one of each, under nothing, over nothing, never moved, never numbered.
- Every write to an outline or its entries locks the outline's row first (`lockOutline`), then its entries; an entry made from a point takes the point (`FOR KEY SHARE`) before that. Do not drop a lock or take them in another order: taken the other way round, a point's deletion and an entry made from it deadlocked when raced. A change of shape goes through `planInsert`, `planMove`, or `planRemove` (`tree.ts`) and `place`, which sets rows aside at negative positions before placing them; do not write `position` or `parent_id` another way, and do not add a CHECK that `position` is not negative.
- A number is never stored and never part of a title. Labels come only from `src/features/outlines/numbering.ts` (`numberOutline`, `entryLabel`), which has no server code and runs in the browser too. A built-in style is stored as its name; a custom one is validated by `numberingConfigSchema` and nothing else. A prefix, suffix, or separator is shown as text only, never as markup. Nothing in `tree.ts` or `numbering.ts` may call itself.
- The shape and the words are counted apart: `sermon_outlines.revision` for add, move, and remove; `outline_entries.revision` for a title, notes, or passages. Keep them apart, keep `expectedRevision` optional, and answer a stale change by writing nothing. An outline action answers with a `code`, the `revision`, and the entry; the editor is to go on from that answer.
- A saved point idea and an outline entry are two things. An entry made from a point (`sourcePointId`) is a copy that remembers its source: never write back to the point, never update entries when a point changes, and never turn `sermon_points` into outline entries or require a row there. Deleting a point clears the link and keeps the entry; that is `ON DELETE SET NULL ("source_point_id")`, a column list written into migration `0013` by hand because Drizzle cannot express it. Never hand-edit `0013` again, and carry that clause into any later migration that touches the key.
- A passage on an entry is five numbers and no translation, as on an idea, validated with `src/features/scripture/reference.ts`, and written only by `setEntryReferences`. Never store verse text on an entry.
- What an account says about itself is three columns on `users`: `church_name`, `ministry_role`, and `attends_preaching_class`. They are validated only by `profileSchemas(locale).profileUpdate` and written only by `saveProfile` behind the `updateProfile` action (`src/features/preferences`), where a field left out is left alone and null or a blank clears a line. Do not write a second action or schema for them (first-time setup is to call the same ones), do not copy them into Clerk metadata, and do not add an onboarding flag or redirect before Phase 4. The name, picture, and email stay Clerk's.
- The ministry role is the person's own words and grants nothing. Never read `ministry_role` to decide access, never turn it into a list, and never confuse it with `users.role`. The administrator's directory leaves the three profile fields out (`withIdentities`); keep it so.
- `attendsPreachingClass` is only ever what the person chose, read through `getPreferences()` on the server and `useAttendsPreachingClass()` in the browser. Never infer it from a role, a context, or the preaching record. It decides what is suggested, in one place (`suggestedContextOptions` leaves out Preaching Class when it is off), and nothing else: changing it never creates, renames, hides, or deletes a context, an occasion, or an idea, and never withholds existing data or ordinary Preaching Record functions from an account that has it off. A new preaching-class surface asks the same preference; do not build a restriction on it.
- Settings is five sections: Personal Information, Church & Ministry, Bible & Language, Appearance & Experience, Account. The theme, the reader's copy shortcut, and the library's card or list view are browser preferences and are not saved to the account.
- Main navigation is `src/components/layout/app-links.ts`. Add the outline page there when it exists. Administration stays in the account menu.
- Dropdowns use `src/components/ui/select.tsx`, not a native `<select>`.
